3 · Auth + request lifecycle

JWT → mirror-row resolve → cache/DB → response

sequenceDiagram
  participant C as Client (RN or portal)
  participant S as Supabase Auth
  participant N as Node API (middleware)
  participant DB as Postgres
  participant R as Redis
  C->>S: sign in (email/pw)
  S-->>C: session JWT (sub, role)
  C->>N: request + Bearer JWT
  N->>S: verify signature (JWKS, cached)
  N->>DB: resolve sub → owners/staff mirror row (upsert on first sight)
  N->>N: enforce role + ownership (no RLS)
  alt cache hit
    N->>R: GET cached read
    R-->>N: value
  else miss / mutation
    N->>DB: query / transaction
    N->>R: set / invalidate keys
  end
  N-->>C: JSON (DATA-CONTRACT.md wire shape)

4 · Group-class enrollment transaction

One-transaction-or-nothing (request-approval & credit-debited booking follow the same shape)

flowchart TD
  A["POST /enrollments
{ cohortId, dogIds[] }"] --> B{"BEGIN txn"}
  B --> C["SELECT cohorts WHERE id=$1 FOR UPDATE"]
  C --> D{"filled + len(dogIds) ≤ capacity ?"}
  D -- no --> E["ROLLBACK → 409 capacity"]
  D -- yes --> F["INSERT len(dogIds) × weeks bookings
(+ booking_dogs, cohort_id, session_report_id)"]
  F --> G["UPDATE cohorts SET filled = filled + len(dogIds)"]
  G --> H["COMMIT"]
  H --> I["invalidate Redis cohorts:{classKey} + enqueue notifications"]

5 · Booking-creation gates

Three unbypassable BEFORE-INSERT trigger floors on every bookings row · staff-owned dogs exempt

flowchart TD
  A["INSERT INTO bookings
(enroll · book · request→convert)"] --> S{"lead dog
staff-owned?"}
  S -- yes --> OK["row inserted
(staff exempt)"]
  S -- no --> P{"owner has a LIVE
card on file?"}
  P -- no --> X1["RAISE → API 4xx
'add a card' (anti-scam)"]
  P -- yes --> V{"lead dog current on
required vaccines?
(America/Chicago)"}
  V -- no --> X2["RAISE → API 422
'vaccine due'"]
  V -- yes --> G{"owner signed current
required agreements?"}
  G -- no --> X3["RAISE → API 422
'sign waiver'"]
  G -- yes --> OK
